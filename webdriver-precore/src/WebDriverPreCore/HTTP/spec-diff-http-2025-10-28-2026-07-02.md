# WebDriver HTTP Protocol Specification Diff: 2025-10-28 to 2026-07-02

This is an AI-generated diff between the [W3C WebDriver Working Draft of 28 October 2025](https://www.w3.org/TR/2025/WD-webdriver2-20251028/) and the [W3C WebDriver Working Draft of 02 July 2026](https://www.w3.org/TR/2026/WD-webdriver2-20260702/).

## Material Changes (Ordered by Significance)

### 1. Visual Viewport Terminology Update (High Impact)

**Section:** 17. Screen capture (lines 5346-5360 in 2026-07-02 spec)

**Change:** All references to "initial viewport" changed to "visual viewport" in screenshot capture functionality.

**Old terminology (2025-10-28):**
- "dumping a snapshot of the initial viewport's framebuffer" (line 5347 in 2025-10-28 spec)
- "capture the top-level browsing context's initial viewport" (line 5349 in 2025-10-28 spec)
- Algorithm steps referenced "initial viewport's width" and "height" (lines 5353-5357 in 2025-10-28 spec)

**New terminology (2026-07-02):**
- "dumping a snapshot of the visual viewport's framebuffer" (line 5349 in 2026-07-02 spec)
- "capture the top-level browsing context's visual viewport" (line 5351 in 2026-07-02 spec)
- Algorithm steps reference "visual viewport's width" and "height" (lines 5355-5359 in 2026-07-02 spec)

**Purpose:** This change aligns WebDriver terminology with the [CSSOM View Module](https://www.w3.org/TR/cssom-view/) definition of "visual viewport," which represents the visual portion of a viewport that is currently visible on screen, excluding scrollbars and other browser UI. The visual viewport can be smaller than the layout viewport on mobile devices when zoomed in.

**Impact:** 
- More accurate screenshot behavior when page is zoomed or on mobile viewports
- Consistent with modern CSS viewport terminology
- Screenshots now explicitly capture what the user sees, not necessarily the entire layout viewport

**W3C Spec Reference:** See the [Screen Capture section](https://www.w3.org/TR/2026/WD-webdriver2-20260702/#screen-capture) and the visual viewport definition in [CSSOM View Module](https://drafts.csswg.org/cssom-view/#visual-viewport).

### 3. Cookie Validation Order Improvement (Medium Impact)

**Section:** Add Cookie command validation (lines 3724-3727 in 2026-07-02 spec)

**Change:** Reordered validation steps to check argument validity before domain validity.

**Old order (2025-10-28, lines 3721-3724):**
1. Check if document is cookie-averse → return `invalid cookie domain`
2. Check if arguments are invalid → return `invalid argument`

**New order (2026-07-02, lines 3724-3727):**
1. Check if arguments are invalid → return `invalid argument`
2. Check if document is cookie-averse or domain mismatch → return `invalid cookie domain`

**Purpose:** Improves error message accuracy by validating argument types and values before checking domain-specific conditions. This follows the general principle of "fail fast" validation where syntax/type errors should be reported before semantic errors.

**Practical benefit:** If a test sends both an invalid argument type (e.g., string instead of boolean for `httpOnly`) AND has a domain mismatch, it will now correctly report `invalid argument` rather than the less helpful `invalid cookie domain`.

**W3C Spec Reference:** See the [Add Cookie command](https://www.w3.org/TR/2026/WD-webdriver2-20260702/#add-cookie) algorithm steps.

### 4. Pointer-Interactable Paint Tree Algorithm Clarification (Low-Medium Impact)

**Section:** Element interactability algorithm (lines 2290-2302 in 2026-07-02 spec)

**Change:** Clarified the definition of center point calculation in the pointer-interactable paint tree algorithm.

**Old wording (2025-10-28, line 2297):**
```
Let center point be the in-view center point of the first indexed element in rectangles.
```

**New wording (2026-07-02, line 2301):**
```
Let center point be the in-view center point of element.
```

**Additional clarification:** The algorithm description now explicitly names the parameter: "An element **element's** pointer-interactable paint tree" (line 2293 in 2026-07-02 spec).

**Purpose:** Removes ambiguity about which center point to use. The old wording suggested using the center of the first rectangle from `getClientRects()`, but the intent was always to use the element's center point directly. The clarification makes the algorithm clearer without changing its behavior.

**Technical note:** The `getClientRects()` call is still performed (line 2297 in 2026-07-02 spec) but its results are only used to check if the element has any rendered rectangles (line 2299), not to determine the center point.

**W3C Spec Reference:** See the [Element Interactability section](https://www.w3.org/TR/2026/WD-webdriver2-20260702/#element-interactability) for the complete algorithm.
